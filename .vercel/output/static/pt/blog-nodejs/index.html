Querido Diário, Eu Continuava Ouvindo Que o Node.js Era Inseguro 🌸

Diário de desenvolvimento da Jill

Por um tempo, eu continuava ouvindo a mesma coisa repetidamente.

"Node.js tem vulnerabilidades demais." "Node não é seguro." "Não use Node para aplicações sérias."

E honestamente—

eu acreditei.

Porque se desenvolvedores suficientes repetem algo…

começa a soar verdadeiro.

Mas quanto mais trabalhava com projetos reais…

mais percebia algo.

A conversa era mais complicada do que eu pensava.

Minha primeira suposição errada

Achei que o próprio Node.js era o problema.

Como se em algum lugar dentro do Node houvesse um grande botão vermelho com a etiqueta: problemas de segurança.

Acontece que—

a maior parte da conversa não é sobre o Node.

É sobre tudo ao redor dele.

Pacotes. Dependências. Versões. Configurações.

E de repente o vilão se tornou muito menos dramático.

Descoberta do dia

Aplicações Node raramente existem sozinhas.

Uma aplicação típica pode se parecer com:

Sua Aplicação → Framework → Dependências → Dependências de dependências → Mais dependências → Ainda mais dependências.

E de repente:

um pacote vulnerável em algum lugar fundo na árvore…

se torna o seu problema.

Foi o momento em que entendi.

O Node não ficou inseguro de repente.

Seu ecossistema ficou muito grande.

Notas Técnicas ✨

Coisas que aprendi enquanto pesquisava e trabalhava com ambientes Node.

1. Instalar um pacote instala… muitos pacotes

Às vezes isso:

npm install nome-do-pacote

na verdade se torna:

1 pacote
↓
32 dependências
↓
145 subdependências
↓
Feito

O que significa: você não instalou uma coisa só. Você instalou uma árvore genealógica inteira.

2. Vulnerabilidades costumam ser descobertas depois

Uma dependência pode estar bem hoje. Depois, meses depois:

Versão 2.4.0
↓
Problema de segurança descoberto
↓
CVE publicado
↓
Atualização recomendada

CVE = Common Vulnerabilities and Exposures. Basicamente: um catálogo público de problemas de segurança conhecidos. Isso foi aterrorizante e fascinante.

3. O npm já oferece ferramentas para ajudar

Um comando que descobri:

npm audit

Exemplo de saída:

3 vulnerabilidades encontradas

1 baixa
1 moderada
1 alta

E então:

npm audit fix

Tenta atualizar o que pode ser corrigido com segurança. Não é mágica. Mas é útil.

4. Atualizar tudo às cegas não é segurança

As pessoas geralmente revisam:

- notas de versão
- mudanças que quebram compatibilidade
- compatibilidade
- atividade do pacote

Este me surpreendeu. Achei que: mais atualizações = mais seguro. Nem sempre. Às vezes as atualizações quebram coisas. O que pareceu irritantemente responsável.

5. Nem todo problema precisa de outra dependência

Quando o JavaScript já tinha:

Array.map()
fetch()
Date()

Este doeu um pouco. Percebi que às vezes eu pesquisava "Como instalo um pacote para fazer isso?" quando a resposta já estava embutida. E de repente entendi por que as pessoas brincam que instalam 200 pacotes.

A parte sobre a qual ninguém me avisou

Segurança geralmente não é dramática.

Ninguém invade sua aplicação usando um capuz.

Na maioria das vezes parece:

pacote desatualizado. configuração fraca. variável de ambiente antiga. validação faltando. dependência esquecida.

O que parece menos cinematográfico.

Quando finalmente fez sentido ✨

A certa altura, parei de perguntar:

"O Node é inseguro?"

E comecei a perguntar:

"Em que estou confiando?"

Isso mudou a forma como vejo os projetos.

Porque cada instalação também é uma decisão.

Cada dependência se torna parte do seu sistema.

E cada atalho eventualmente vira manutenção.

Bônus: Coisas às quais agora presto mais atenção

Antes de adicionar uma dependência:

Posso construir isso?
↓
É mantido ativamente?
↓
Tem lançamentos recentes?
↓
Quantos downloads tem?
↓
Tem problemas de segurança abertos?
↓
Eu realmente preciso disso?

Não porque tudo seja perigoso. Mas porque tudo tem compensações.

Nota pessoal 🌸

Como ariana, descobrir que minha aplicação secretamente continha 300 pacotes pareceu pessoalmente ofensivo.

Instalei uma coisa só.

Uma.

Por que de repente temos um ecossistema.

A lição real 💖

O Node.js não ficou inseguro de repente.

Simplesmente comecei a entender que o desenvolvimento moderno não é apenas escrever código.

É também escolher em qual código confiar.

E honestamente—

isso parece um problema muito mais interessante.

Coisas Que Quero Lembrar 🌷

  • ✦Dependências são parte da arquitetura
  • ✦Atualizar merece estratégia
  • ✦Segurança geralmente é acumulação
  • ✦Simplicidade reduz riscos
  • ✦Cada instalação é uma decisão
