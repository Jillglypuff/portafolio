Querido Diário, Ninguém Me Disse Que APIs Eram Conversas 🌸

Diário de desenvolvimento da Jill

Quando aprendi sobre APIs pela primeira vez, elas pareciam... mecânicas.

Você envia uma requisição. Recebe uma resposta. Pronto.

Parecia uma máquina de vendas.

Insira a requisição. Receba o JSON. Siga em frente.

Mas depois de trabalhar em aplicações reais...

Percebi que APIs não são apenas requisições.

São conversas entre sistemas.

E como qualquer boa conversa... ambos os lados precisam se entender.

Minha primeira suposição errada

No início, achei que construir uma API significava criar rotas como estas:

GET/users
POST/orders
DELETE/products/15

Se o endpoint retornasse dados... eu considerava concluído.

Técnicamente, funcionava.

Mas eu não estava realmente pensando no desenvolvedor que iria consumi-la.

Então percebi uma coisa.

A API não é construída para mim. É construída para quem tiver que se integrar a ela.

Isso muda tudo.

APIs são contratos

Um dos conceitos mais importantes que aprendi é que APIs são contratos.

Se um lado muda... o outro lado pode quebrar.

Imagine um frontend esperando esta resposta:

JSON Esperado
{
  "id": 15,
  "name": "Jill"
}
⚡
Backend Alterado
{
  "userId": 15,    // ❌ Error
  "fullName": "Jill Hernandez"
}

A API ainda funciona. O servidor não cai. Mas o frontend de repente para de funcionar. Nada está tecnicamente "errado". O contrato foi simplesmente quebrado.

Uma boa API responde a perguntas

O endpoint em si não é o produto. A resposta é.

Uma resposta deve responder a perguntas de forma clara. Por exemplo, em vez de retornar:

Máquina de Vendas
{
  "status": true
}
Conversação
{
  "success": true,
  "message": "Fatura gerada com sucesso.",
  "invoiceId": 2487
}

O consumidor sabe imediatamente: O que aconteceu, Se deu certo, O que fazer a seguir. Isso é comunicação.

Métodos HTTP têm significado

Uma coisa que me ajudou a entender melhor as APIs foi perceber que os métodos HTTP não são aleatórios.

Cada um representa uma intenção.

MétodoPropósito
GETRecuperar informações
POSTCriar recursos
PUTSubstituir recursos
PATCHAtualizar parte de um recurso
DELETERemover recursos

Usar o método correto torna uma API previsível. Os desenvolvedores não deveriam ter que adivinhar o que um endpoint faz.

Códigos de status importam

Retornar dados não é suficiente. O código de status HTTP conta a primeira parte da história.

200 OKTudo funcionou.
201 CreatedUm novo recurso foi criado.
400 Bad RequestO cliente enviou dados inválidos.
401 UnauthorizedA autenticação é necessária.
404 Not FoundO recurso não existe.
500 Internal Server ErrorAlgo falhou no servidor.

Uma boa API se comunica tanto através do corpo da resposta quanto do código de status.

Projetar antes de programar

Um hábito que comecei a adotar é definir os endpoints antes de escrever a lógica de negócios. Algo tão simples como:

GET/products
GET/products/{id}
POST/orders
PATCH/orders/{id}
DELETE/cart/{id}

Isso ajuda a responder a perguntas cedo. Como o frontend consumirá isso? O aplicativo móvel usará o mesmo endpoint? Outro serviço precisará dessa informação mais tarde? Projete primeiro. Implemente depois.

APIs devem tornar erros fáceis de entender

Uma das melhores experiências para um desenvolvedor é receber um erro que realmente explica o problema. Em vez de:

Genérico
{
  "error": true
}
Descritivo
{
  "success": false,
  "error": "E-mail já cadastrado.",
  "field": "email"
}

Boas mensagens de erro reduzem o tempo de depuração. E tornam as integrações muito mais suaves.

O versionamento existe por uma razão

As aplicações evoluem. APIs evoluem também. Às vezes, alterar um endpoint não é suficiente.

É aí que o versionamento se torna importante.

v1
/api/v1/products
v2
/api/v2/products

Manter versões anteriores permite que as aplicações existentes continuem funcionando enquanto os novos clientes adotam a API atualizada. É outra maneira de respeitar o contrato.

A documentação é parte da API

Uma lição que eu não esperava aprender: se uma API não for documentada... alguém eventualmente lerá o código-fonte para entendê-la.

Uma boa documentação explica: Endpoints disponíveis, Parâmetros, Autenticação, Exemplos de requisições, Exemplos de respostas, Códigos de erro.

Ferramentas como Postman, Swagger/OpenAPI e Insomnia tornam esse processo muito mais fácil.

Uma API bem documentada costuma ser mais fácil de integrar do que uma tecnicamente perfeita, mas sem documentação.

Conclusão técnica 🌸

Uma API bem projetada deve ser:

  • ✔Previsível
  • ✔Consistente
  • ✔Versionada
  • ✔Bem documentada
  • ✔Fácil de consumir
  • ✔Fácil de depurar

O objetivo não é apenas trocar dados. É criar uma conversa confiável entre sistemas.

Nota pessoal 🌷

Quanto mais trabalho de backend eu faço... menos penso em endpoints. Agora penso em comunicação.

Cada resposta é algo que outro desenvolvedor —ou outra aplicação— precisa entender. Essa pequena mudança transformou completamente como projeto APIs.

Em vez de perguntar: "Esse endpoint funciona?" agora pergunto: "Outro desenvolvedor gostaria de se integrar com ele?" E acho essa uma pergunta muito melhor.

Coisas Que Quero Lembrar 💖

  • ✦APIs são conversas, não apenas endpoints.
  • ✦Métodos HTTP funcionam como intenções.
  • ✦Códigos de status fazem parte da mensagem.
  • ✦Quebrar um contrato quebra a confiança.
  • ✦Uma boa documentação é um recurso, não um detalhe esquecido.
