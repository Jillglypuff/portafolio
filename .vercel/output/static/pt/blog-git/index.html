Querido Diário, Por Que Todo Desenvolvedor Deve Aprender Git Além de git push 🌸

Diário de desenvolvimento da Jill

Quando comecei a usar o Git... meu fluxo de trabalho parecia mais ou menos assim.

git add . → git commit -m "changes" → git push

Isso era tudo.

Contanto que meu código chegasse ao GitHub, eu achava que estava usando o Git corretamente.

Acontece que... eu estava usando apenas uma fração minúscula do que o Git realmente pode fazer.

Minha primeira suposição errada

Por muito tempo, pensei que o Git era simplesmente um backup. Escrever código. Commit. Push. Repetir.

Mas o Git não é o Dropbox para desenvolvedores. O Git é um sistema de controle de versão completo projetado para ajudar as pessoas a construírem software juntas.

Ele se lembra de cada decisão. Cada mudança. Cada experimento. Cada erro. E isso é incrivelmente poderoso.

Git não é o GitHub

Uma das primeiras coisas que me confundiu foi achar que Git e GitHub eram a mesma coisa. Eles não são.

O Git é o sistema de controle de versão. O GitHub é uma plataforma que hospeda repositórios Git.

Você pode usar o Git sem o GitHub. E você pode usar o GitHub porque o Git existe.

Entender essa distinção torna muitos conceitos do Git muito mais fáceis.

Cada commit conta uma história

Um commit não deve apenas salvar código. Deve explicar o porquê de algo ter mudado.

Em vez de mensagens de commit sem sentido:
git commit -m "update"
git commit -m "changes"
git commit -m "fix"
Tente escrever mensagens descritivas:
git commit -m "Add payment validation before checkout"
git commit -m "Fix responsive navigation on iPad"

Meses depois... seu eu do futuro ficará incrivelmente grato.

Ramos são universos paralelos

Um conceito de que gosto muito é a ramificação (branching).

Imagine que seu projeto está em uma linha do tempo única (main). Agora você precisa de um novo recurso.

Em vez de arriscar o código de produção... você cria um ramo (branch). Cada branch torna-se um espaço de trabalho isolado onde você pode experimentar com segurança.

main
feature/payment
feature/profile

Conflitos de mesclagem não são o Git sendo chato

No começo... os conflitos de mesclagem (merge conflicts) pareciam assustadores. Achei que tinha quebrado o repositório.

Geralmente, o Git está simplesmente dizendo: "Duas pessoas alteraram a mesma parte do código. Não sei qual versão você quer."

Por exemplo, se o Desenvolvedor A e o Desenvolvedor B editarem a mesma variável de imposto de forma diferente, o Git não pode adivinhar. Então, ele pede para você resolver o conflito.

Representação do conflito no arquivo:

<<<<<<< HEAD
const tax = 13;
=======
const tax = 15;
>>>>>>> feature/tax

O Git te ajuda a viajar no tempo

Um dos meus recursos favoritos do Git é poder inspecionar o histórico e comparar mudanças.

Depois que entendi isso... parei de ter medo de cometer erros. Porque a maioria dos erros é recuperável.

Pull Requests são conversas

Uma coisa que eu não valorizava no início é que Pull Requests não servem apenas para mesclar código. Eles são sobre comunicação.

Um bom Pull Request explica o que mudou, o porquê e quaisquer riscos envolvidos. As revisões de código geralmente melhoram o software muito antes de os usuários o verem.

O Git torna o trabalho em equipe possível

Sem controle de versão... a colaboração vira um caos.

O Git permite que vários desenvolvedores trabalhem em recursos, revisem códigos, acompanhem alterações e recuperem versões anteriores. Projetos de software grandes simplesmente não seriam práticos sem ele.

Meus comandos Git mais usados

Com o tempo, eles se tornaram parte do meu fluxo de trabalho diário. Note que apenas um deles é o git push! O resto me ajuda a entender e gerenciar o projeto.

git statusMostra o status do diretório de trabalho
git pullBusca e integra com outro repositório
git addAdiciona conteúdo do arquivo ao índice
git commitGrava as alterações no repositório
git pushAtualiza chaves remotas e objetos associados
git checkoutAlterna ramos ou restaura arquivos
git switchAlterna ramos facilmente
git branchLista, cria ou deleta ramos
git mergeJunta dois ou mais históricos
git logMostra os logs de confirmação
git diffMostra alterações entre confirmações e diretório

Conclusão técnica 🌸

O Git não serve apenas para enviar código para o GitHub. É sobre gerenciar mudanças.

Boas práticas de Git incluem:

  • ✔Commits pequenos e significativos
  • ✔Mensagens de commit claras
  • ✔Ramos de recursos (feature branches)
  • ✔Pull Requests
  • ✔Revisões de código
  • ✔Manter a main estável

Aprender esses hábitos cedo torna a colaboração muito mais fácil.

Nota pessoal 🌷

Uma das coisas que gosto no desenvolvimento de software é perceber que cada ferramenta tem camadas.

No começo, o Git parecia uma lista de comandos para memorizar. Agora... parece mais uma linha do tempo. Um registro de como uma ideia evoluiu.

Cada commit representa uma pequena decisão. Cada branch representa um experimento. E cada mesclagem conta parte da história do software. Acho que é uma bela maneira de encarar o controle de versão.

Coisas Que Quero Lembrar 💖

  • ✦Git e GitHub são coisas diferentes.
  • ✦Os commits devem explicar o porquê, não apenas o quê.
  • ✦Os ramos tornam a experimentação segura.
  • ✦Conflitos de mesclagem são conversas, não desastres.
  • ✦O controle de versão é uma das ferramentas mais importantes que um desenvolvedor pode aprender.
