Dear Diary, No One Told Me APIs Were Conversations 🌸

A developer diary by Jill

When I first learned about APIs, they felt... mechanical.

You send a request. You receive a response. Done.

It sounded like a vending machine.

Insert request. Receive JSON. Move on.

But after working on real applications...

I realized APIs aren't just requests.

They're conversations between systems.

And like any good conversation... both sides need to understand each other.

My first misconception

At the beginning, I thought building an API meant creating routes like these:

GET/users
POST/orders
DELETE/products/15

If the endpoint returned data... I considered it finished.

Técnicamente, it worked.

But I wasn't really thinking about the developer who would consume it.

Then I realized something.

The API isn't built for me. It's built for whoever has to integrate with it.

That changes everything.

APIs are contracts

One of the most important concepts I learned is that APIs are contracts.

If one side changes... the other side can break.

Imagine a frontend expecting this response:

Expected JSON
{
  "id": 15,
  "name": "Jill"
}
⚡
Changed Backend
{
  "userId": 15,    // ❌ Error
  "fullName": "Jill Hernandez"
}

The API still works. The server doesn't crash. But the frontend suddenly stops working. Nothing is technically "wrong." The contract was simply broken.

A good API answers questions

The endpoint itself isn't the product. The response is.

A response should answer questions clearly. For example, instead of returning:

Vending Machine (Not helpful)
{
  "status": true
}
Conversation (Helpful)
{
  "success": true,
  "message": "Invoice generated successfully.",
  "invoiceId": 2487
}

The consumer immediately knows: What happened, whether it succeeded, and what to do next. That's communication.

HTTP methods have meaning

One thing that helped me understand APIs better was realizing HTTP methods aren't random.

Each one represents an intention.

MethodPurpose
GETRetrieve information
POSTCreate resources
PUTReplace resources
PATCHUpdate part of a resource
DELETERemove resources

Using the correct method makes an API predictable. Developers shouldn't have to guess what an endpoint does.

Status codes matter

Returning data isn't enough. The HTTP status code tells the first part of the story.

200 OKEverything worked.
201 CreatedA new resource was created.
400 Bad RequestThe client sent invalid data.
401 UnauthorizedAuthentication is required.
404 Not FoundThe resource doesn't exist.
500 Internal Server ErrorSomething failed on the server.

A good API communicates through both its response body and its status code.

Designing before coding

One habit I've started adopting is defining the endpoints before writing business logic. Something as simple as:

GET/products
GET/products/{id}
POST/orders
PATCH/orders/{id}
DELETE/cart/{id}

This helps answer questions early. How will the frontend consume this? Will the mobile app use the same endpoint? Will another service need this information later? Design first. Implement second.

APIs should make mistakes easy to understand

One of the best developer experiences is receiving an error that actually explains the problem. Instead of:

Generic (Frustrating)
{
  "error": true
}
Descriptive (Awesome)
{
  "success": false,
  "error": "Email already exists.",
  "field": "email"
}

Good error messages reduce debugging time. And they make integrations much smoother.

Versioning exists for a reason

Applications evolve. APIs evolve too. Sometimes changing an endpoint isn't enough.

That's where versioning becomes important.

v1
/api/v1/products
v2
/api/v2/products

Maintaining older versions allows existing applications to continue working while newer clients adopt the updated API. It's another way of respecting the contract.

Documentation is part of the API

One lesson I didn't expect to learn: If an API isn't documented... someone will eventually read the source code to understand it.

Good documentation explains: Available endpoints, parameters, authentication, request examples, response examples, and error codes.

Tools like Postman, Swagger/OpenAPI, and Insomnia make this process much easier.

A well-documented API is often easier to integrate than a technically perfect one with no documentation.

Technical takeaway 🌸

A well-designed API should be:

  • ✔Predictable
  • ✔Consistent
  • ✔Versioned
  • ✔Well documented
  • ✔Easy to consume
  • ✔Easy to debug

The goal isn't just to exchange data. It's to create a reliable conversation between systems.

Personal note 🌷

The more backend work I've done... the less I think about endpoints. Now I think about communication.

Every response is something another developer—or another application—has to understand. That small shift completely changed how I design APIs.

Instead of asking: "Does this endpoint work?" I now ask: "Would another developer enjoy integrating with it?" And I think that's a much better question.

Things I Want To Remember 💖

  • ✦APIs are conversations, not just endpoints.
  • ✦HTTP methods communicate intent.
  • ✦Status codes are part of the message.
  • ✦Breaking a contract breaks trust.
  • ✦Good documentation is a feature, not an afterthought.

— Jill
