Dear Diary, I Finally Understood SaaS, PaaS, and IaaS 🌸

A developer diary by Jill

I thought cloud computing was just "someone else's computer."

Turns out, it's really about deciding what you want to manage—and what you don't.

Cloud computing used to sound like one of those topics everyone casually understood except me.

People would say things like:

"We'll deploy it to the cloud."

Or: "We'll use a PaaS."

Everyone nodded.

I nodded too.

Did I fully understand the difference?

Absolutely not.

My first misconception

In my head, cloud services looked something like this:

Write code → Deploy → Internet magic ✨ → Application is online

It felt simple.

Until I started deploying my own projects and realized that someone, somewhere, is responsible for much more than just running the application.

Servers. Operating systems. Networking. Security. Scaling. Monitoring. Backups.

And suddenly those three acronyms started making a lot more sense.

Three layers, three different responsibilities

One of the easiest ways to understand cloud services is by asking:

Who is responsible for what?

The more responsibility the provider takes, the less infrastructure you need to manage.

Technical Notes ✨

Things I learned while researching cloud services.

1. IaaS — Infrastructure as a Service

Typical responsibilities:

You manage:
✔ Operating System
✔ Runtime
✔ Application
✔ Database
✔ Security

Provider manages:
✔ Physical hardware
✔ Networking
✔ Virtualization

Common providers:

Amazon EC2
Microsoft Azure Virtual Machines
Google Compute Engine
DigitalOcean Droplets

IaaS offers maximum flexibility... but also maximum responsibility.

2. PaaS — Platform as a Service

Typical workflow:

Push code
↓
Platform builds application
↓
Deploy
↓
Application is online

Examples:

Vercel
Render
Railway
Heroku

This is exactly why I enjoy deploying my portfolio on Vercel. I don't need to configure Linux. I don't need to install Node. I don't need to worry about web servers. I simply focus on building the application.

3. SaaS — Software as a Service

Examples:

GitHub
Notion
Figma
Slack
Google Docs
Canva

This one is actually the easiest. You don't build the software. You simply use it. The provider manages everything. You only need an account.

4. Real examples from my own projects

While building my portfolio, my stack looked something like this:

Vue
↓
Vercel (PaaS)
↓
Custom Domain

For designing interfaces / For storing project data:

Figma

Supabase

Supabase is interesting because it provides multiple managed services, including PostgreSQL databases, authentication, storage, and APIs. It allows developers to focus more on application logic instead of managing infrastructure.

Visualizing the difference

SaaS — You use software

↓

PaaS — You build software

↓

IaaS — You build and manage infrastructure

The lower you go...

the more control you gain.

the more responsibility you accept.

Why does this matter? ✨

Understanding these concepts changes how you think about architecture.

Instead of asking: "Which cloud service should I use?"

You start asking:

How much control do I need?

How much maintenance do I want?

How much time do I want to spend managing servers?

Can I let someone else handle the infrastructure?

Those questions usually matter more than the technology itself.

Personal note 🌷

As an Aries, discovering that someone else could manage the servers for me felt like excellent news.

I enjoy building applications.

I don't necessarily dream about configuring Linux at 2 a.m.

Maybe one day.

Not today.

Technical takeaway 🌸

There isn't a "best" option.

Each model solves different problems.

SaaS: Using software without managing infrastructure.

PaaS: Developing and deploying applications quickly.

IaaS: Full infrastructure control and custom environments.

Choosing between them is an architectural decision, not just a technical one.

Things I Want To Remember 💖

  • ✦Cloud computing isn't one thing—it's a collection of service models
  • ✦More control usually means more responsibility
  • ✦PaaS lets me focus on building instead of maintaining infrastructure
  • ✦SaaS powers many of the tools I already use every day
  • ✦Good architecture starts with understanding trade-offs
