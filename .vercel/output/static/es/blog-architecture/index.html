Querido Diario, Arquitectura Antes que Código 🌸

El diario de desarrollo de Jill

Abre el IDE. Crea un proyecto. Comienza a escribir código. Conviértete en desarrollador de software.

Simple. Muy cinematográfico. Muy inexacto.

Mientras más proyectos he trabajado...

más me he dado cuenta de algo.

Escribir código suele ser uno de los últimos pasos.

Mi primer supuesto incorrecto

Cuando comencé a aprender desarrollo de software, me imaginaba que los desarrolladores experimentados pasaban la mayor parte del día escribiendo código.

Escribiendo rápido. Cambiando entre terminales. Construyendo características sin parar.

La realidad se ve muy diferente.

Una gran parte del desarrollo de software es en realidad:

  • 🌸Pensar
  • 🌸Leer
  • 🌸Hacer preguntas
  • 🌸Cambiar decisiones
  • 🌸Revisar requisitos
  • 🌸Diseñar

Y de repente... han pasado dos horas y has escrito doce líneas de código.

El software comienza con preguntas

Antes de elegir un framework. Antes de crear una base de datos. Antes de escribir una API.

Alguien tiene que responder preguntas como:

  • ?¿Quién va a usar esto?
  • ?¿Qué problema estamos resolviendo?
  • ?¿Cuál es la versión más pequeña que podemos construir?
  • ?¿Qué pasa si algo falla?
  • ?¿Qué información necesitamos realmente?
  • ?¿Necesita autenticación?
  • ?¿Soportará múltiples idiomas?
  • ?¿Eventualmente se convertirá en una aplicación móvil?

A veces... una sola respuesta cambia toda la arquitectura.

La arquitectura invisible

La mayoría de los usuarios solo ven la interfaz final. Los desarrolladores saben que eso es solo la superficie.

Una aplicación típica generalmente comienza a verse más como esto:

01Idea
02Investigación
03Requisitos
04Flujos de Usuario
05Wireframes
06Arquitectura
07Diseño de Base de Datos
08Diseño de API
09Desarrollo
10Pruebas
11Despliegue
12Mantenimiento

El código es solo una parte de ese viaje.

Diseñar antes de desarrollar

Una cosa que he comenzado a apreciar mucho más es diseñar la aplicación antes de construirla.

A veces eso significa wireframes, flujos de usuario, storyboards o prototipos de Figma.

El objetivo no es hacer algo hermoso. Es responder preguntas antes de que se conviertan en errores.

Mover un botón en Figma toma segundos. Mover todo un flujo de trabajo después del desarrollo puede tomar días.

Las bases de datos merecen más respeto

Una lección que he aprendido es que cambiar una base de datos rara vez es "solo agregar una columna".

Una estructura simple podría comenzar así:

Tabla de Usuarios
  • id INT PRIMARY KEY
  • name VARCHAR
  • email VARCHAR UNIQUE
Tabla de Pedidos
  • id INT PRIMARY KEY
  • user_id INT FOREIGN KEY
  • status VARCHAR
  • total DECIMAL

Parece simple. Hasta que alguien pregunta:

  • ✦"¿Puede un pedido tener múltiples envíos?"
  • ✦"¿Puede un usuario tener múltiples direcciones de facturación?"

Las pequeñas decisiones de negocio a menudo se convierten en decisiones de base de datos. Y las decisiones de base de datos tienden a quedarse con el proyecto durante mucho tiempo.

Las APIs son contratos

Una cosa que disfruto del desarrollo backend es diseñar APIs.

No porque escribir endpoints sea difícil. Sino porque las APIs definen cómo se comunica cada parte de la aplicación.

A veces la conversación comienza antes de que exista un solo endpoint.

GET/products
POST/orders
PATCH/users/{id}
DELETE/cart/{item}

Cambiar un endpoint más tarde puede afectar: Aplicaciones móviles, Frontend, Integraciones, Documentación, Pruebas automatizadas.

Una API no es solo código. Es un contrato.

Luego viene el código

Solo después de entender el problema comienza realmente el desarrollo.

El framework importa. El lenguaje importa. Pero importan menos que las decisiones tomadas de antemano.

Laravel. Vue. React. Node.js. React Native.

Todos son herramientas.

Una buena arquitectura hace que esas herramientas sean más fáciles de usar. Una mala arquitectura hace que cada framework se sienta difícil.

El despliegue no es la línea de meta

Mucha gente imagina el despliegue como el último paso. En realidad... suele ser el comienzo.

Después de producción viene: Monitoreo, Corrección de errores, Mejoras de rendimiento, Comentarios de los usuarios, Nuevos requisitos, Nuevas versiones.

El software rara vez está "terminado". Evoluciona.

Conclusión técnica 🌸

Un concepto que me ayudó a entender mejor el desarrollo de software es el Ciclo de Vida del Desarrollo de Software (SDLC).

Agile no elimina estas etapas. Simplemente las repite en iteraciones más pequeñas. Cada sprint es otra oportunidad para mejorar el producto.

SDLC (Software Development Life Cycle):

Requisitos
→
Diseño
→
Desarrollo
→
Pruebas
→
Despliegue
→
Mantenimiento

Nota personal 🌷

Uno de los proyectos que estoy construyendo actualmente comenzó como una idea simple. Un sitio web. Eso es todo.

Meses después... incluye autenticación, procesamiento de pagos, mapas, logística, paneles administrativos y varias ideas de automatización que todavía están en mi pizarra.

El proyecto no se volvió más complejo porque escribí más código. Se volvió más complejo porque entendí mejor el problema.

Y creo que esa es una de las partes más interesantes de la ingeniería de software.

Mientras más aprendes... más te das cuenta de que el buen software comienza mucho antes del primer commit.

Cosas Que Quiero Recordar 💖

  • ✦El código es solo una fase del desarrollo de software.
  • ✦La buena arquitectura ahorra tiempo más tarde.
  • ✦Las bases de datos merecen una planificación cuidadosa.
  • ✦Las APIs son contratos, no solo endpoints.
  • ✦Las mejores decisiones de ingeniería a menudo ocurren antes de escribir código.
