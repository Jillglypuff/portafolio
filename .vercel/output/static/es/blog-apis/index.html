Querido Diario, Nadie Me Dijo Que las APIs Eran Conversaciones 🌸

El diario de desarrollo de Jill

Cuando aprendí por primera vez sobre las APIs, se sentían... mecánicas.

Envías una solicitud. Recibes una respuesta. Listo.

Sonaba como una máquina expendedora.

Insertas la solicitud. Recibes el JSON. Siguiente.

Pero después de trabajar en aplicaciones reales...

Me di cuenta de que las APIs no son solo solicitudes.

Son conversaciones entre sistemas.

Y como en cualquier buena conversación... ambas partes deben entenderse.

Mi primer supuesto incorrecto

Al principio, pensé que construir una API significaba crear rutas como estas:

GET/users
POST/orders
DELETE/products/15

Si el endpoint devolvía datos... lo consideraba terminado.

Técnicamente, funcionaba.

Pero no estaba pensando realmente en el desarrollador que la consumiría.

Entonces me di cuenta de algo.

La API no está construida para mí. Está construida para quien tenga que integrarse con ella.

Eso lo cambia todo.

Las APIs son contratos

Uno de los conceptos más importantes que aprendí es que las APIs son contratos.

Si un lado cambia... el otro lado puede romperse.

Imagina un frontend que espera esta respuesta:

JSON Esperado
{
  "id": 15,
  "name": "Jill"
}
⚡
Backend Modificado
{
  "userId": 15,    // ❌ Error
  "fullName": "Jill Hernandez"
}

La API sigue funcionando. El servidor no se cae. Pero el frontend de repente deja de funcionar. Nada está técnicamente "mal". El contrato simplemente se rompió.

Una buena API responde preguntas

El endpoint en sí no es el producto. La respuesta lo es.

Una respuesta debería responder preguntas claramente. Por ejemplo, en lugar de devolver:

Máquina Expendedora
{
  "status": true
}
Conversación
{
  "success": true,
  "message": "Factura generada correctamente.",
  "invoiceId": 2487
}

El consumidor sabe inmediatamente: Qué pasó, si tuvo éxito, qué hacer a continuación. Eso es comunicación.

Los métodos HTTP tienen significado

Una cosa que me ayudó a entender mejor las APIs fue darme cuenta de que los métodos HTTP no son aleatorios.

Cada uno representa una intención.

MétodoPropósito
GETObtener información
POSTCrear recursos
PUTReemplazar recursos
PATCHActualizar parte de un recurso
DELETEEliminar recursos

Usar el método correcto hace que una API sea predecible. Los desarrolladores no deberían tener que adivinar qué hace un endpoint.

Los códigos de estado importan

Devolver datos no es suficiente. El código de estado HTTP cuenta la primera parte de la historia.

200 OKTodo funcionó.
201 CreatedSe creó un nuevo recurso.
400 Bad RequestEl cliente envió datos no válidos.
401 UnauthorizedSe requiere autenticación.
404 Not FoundEl recurso no existe.
500 Internal Server ErrorAlgo falló en el servidor.

Una buena API se comunica tanto a través de su cuerpo de respuesta como de su código de estado.

Diseñar antes de programar

Un hábito que he comenzado a adoptar es definir los endpoints antes de escribir la lógica de negocio. Algo tan simple como:

GET/products
GET/products/{id}
POST/orders
PATCH/orders/{id}
DELETE/cart/{id}

Esto ayuda a responder preguntas temprano. ¿Cómo consumirá esto el frontend? ¿Usará la aplicación móvil el mismo endpoint? ¿Otro servicio necesitará esta información más adelante? Diseñar primero. Implementar después.

Las APIs deberían hacer que los errores sean fáciles de entender

Una de las mejores experiencias para un desarrollador es recibir un error que realmente explique el problema. En lugar de:

Genérico
{
  "error": true
}
Descriptivo
{
  "success": false,
  "error": "El correo electrónico ya existe.",
  "field": "email"
}

Los buenos mensajes de error reducen el tiempo de depuración. Y hacen que las integraciones sean mucho más fluidas.

El control de versiones existe por una razón

Las aplicaciones evolucionan. Las APIs también. A veces, cambiar un endpoint no es suficiente.

Ahí es donde el control de versiones se vuelve importante.

v1
/api/v1/products
v2
/api/v2/products

Mantener versiones anteriores permite que las aplicaciones existentes sigan funcionando mientras los nuevos clientes adoptan la API actualizada. Es otra forma de respetar el contrato.

La documentación es parte de la API

Una lección que no esperaba aprender: si una API no está documentada... alguien eventualmente leerá el código fuente para entenderla.

La buena documentación explica: Endpoints disponibles, Parámetros, Autenticación, Ejemplos de solicitudes, Ejemplos de respuestas, Códigos de error.

Herramientas como Postman, Swagger/OpenAPI e Insomnia facilitan mucho este proceso.

Una API bien documentada suele ser más fácil de integrar que una técnicamente perfecta pero sin documentación.

Conclusión técnica 🌸

Una API bien diseñada debería ser:

  • ✔Predecible
  • ✔Consistente
  • ✔Versionada
  • ✔Bien documentada
  • ✔Fácil de consumir
  • ✔Fácil de depurar

El objetivo no es solo intercambiar datos. Es crear una conversación confiable entre sistemas.

Nota personal 🌷

Mientras más trabajo de backend he hecho... menos pienso en endpoints. Ahora pienso en comunicación.

Cada respuesta es algo que otro desarrollador —o otra aplicación— tiene que entender. Ese pequeño cambio transformó por completo cómo diseño las APIs.

En lugar de preguntar: "¿Funciona este endpoint?" ahora pregunto: "¿Disfrutaría otro desarrollador integrándose con él?" Y creo que esa es una pregunta mucho mejor.

Cosas Que Quiero Recordar 💖

  • ✦Las APIs son conversaciones, no solo endpoints.
  • ✦Los métodos HTTP comunican la intención.
  • ✦Los códigos de estado son parte del mensaje.
  • ✦Romper un contrato rompe la confianza.
  • ✦La buena documentación es una característica, no una ocurrencia de último momento.
