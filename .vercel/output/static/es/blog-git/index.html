Querido Diario, Por Qué Cada Desarrollador Debería Aprender Git Más Allá de git push 🌸

El diario de desarrollo de Jill

Cuando comencé a usar Git... mi flujo de trabajo se veía más o menos así.

git add . → git commit -m "changes" → git push

Eso era todo.

Mientras mi código llegara a GitHub, pensaba que estaba usando Git correctamente.

Resulta que... solo estaba usando una pequeña fracción de lo que Git realmente puede hacer.

Mi primer supuesto incorrecto

Durante mucho tiempo pensé que Git era simplemente un respaldo. Escribir código. Confirmar. Subir. Repetir.

Pero Git no es Dropbox para desarrolladores. Git es un sistema de control de versiones completo diseñado para ayudar a las personas a construir software juntas.

Recuerda cada decisión. Cada cambio. Cada experimento. Cada error. Y eso es increíblemente poderoso.

Git no es GitHub

Una de las primeras cosas que me confundió fue pensar que Git y GitHub eran lo mismo. No lo son.

Git es el sistema de control de versiones. GitHub es una plataforma que aloja repositorios de Git.

Puedes usar Git sin GitHub. Y puedes usar GitHub porque Git existe.

Entender esa distinción hace que muchos conceptos de Git sean mucho más fáciles.

Cada commit cuenta una historia

Un commit no debería solo guardar código. Debería explicar por qué cambió algo.

En lugar de mensajes de commit sin sentido:
git commit -m "update"
git commit -m "changes"
git commit -m "fix"
Intenta escribir mensajes descriptivos:
git commit -m "Add payment validation before checkout"
git commit -m "Fix responsive navigation on iPad"

Meses después... tu yo del futuro te estará increíblemente agradecido.

Las ramas son universos paralelos

Un concepto que realmente disfruto es el de las ramas (branching).

Imagina que tu proyecto está en una sola línea de tiempo (main). Ahora necesitas una nueva funcionalidad.

En lugar de arriesgar el código de producción... creas una rama. Cada rama se convierte en un espacio de trabajo aislado donde puedes experimentar de forma segura.

main
feature/payment
feature/profile

Los conflictos de fusión no son Git siendo malo

Al principio... los conflictos de fusión (merge conflicts) se sentían aterradores. Pensaba que había roto el repositorio.

Por lo general, Git simplemente está diciendo: "Dos personas cambiaron la misma parte del código. No sé qué versión quieres."

Por ejemplo, si el Desarrollador A y el Desarrollador B editan la misma variable de impuestos de manera diferente, Git no puede adivinar. Así que te pide que resuelvas el conflicto.

Representación del conflicto en el archivo:

<<<<<<< HEAD
const tax = 13;
=======
const tax = 15;
>>>>>>> feature/tax

Git te ayuda a viajar en el tiempo

Una de mis características favoritas de Git es poder inspeccionar el historial y comparar cambios.

Una vez que entendí esto... dejé de tener miedo de cometer errores. Porque la mayoría de los errores son recuperables.

Los Pull Requests son conversaciones

Una cosa que no aprecié al principio es que los Pull Requests no son solo para fusionar código. Se tratan de comunicación.

Un buen Pull Request explica qué cambió, por qué y cualquier riesgo involucrado. Las revisiones de código a menudo mejoran el software mucho antes de que los usuarios lo vean.

Git hace posible el trabajo en equipo

Sin control de versiones... la colaboración se convierte en un caos.

Git permite a múltiples desarrolladores trabajar en características, revisar código, realizar un seguimiento de los cambios y recuperar versiones anteriores. Los proyectos de software grandes simplemente no serían prácticos sin él.

Mis comandos de Git más utilizados

Con el tiempo, estos se han convertido en parte de mi flujo de trabajo diario. ¡Nota que solo uno de ellos es git push! El resto me ayuda a comprender y administrar el proyecto.

git statusMuestra el estado del árbol de trabajo
git pullBusca e integra con otro repositorio
git addAgrega el contenido del archivo al índice
git commitGraba los cambios en el repositorio
git pushActualiza las referencias remotas y objetos asociados
git checkoutCambia de rama o restaura archivos
git switchCambia de rama fácilmente
git branchLista, crea o elimina ramas
git mergeUne dos o más historiales de desarrollo
git logMuestra los registros de commits
git diffMuestra cambios entre commits y árbol de trabajo

Conclusión técnica 🌸

Git no se trata solo de enviar código a GitHub. Se trata de gestionar el cambio.

Las buenas prácticas de Git incluyen:

  • ✔Commits pequeños y significativos
  • ✔Mensajes de commit claros
  • ✔Ramas de funcionalidad (feature branches)
  • ✔Pull Requests
  • ✔Revisiones de código
  • ✔Mantener main estable

Aprender estos hábitos temprano hace que la colaboración sea mucho más fácil.

Nota personal 🌷

Una de las cosas que disfruto del desarrollo de software es darme cuenta de que cada herramienta tiene capas.

Al principio, Git se sentía como una lista de comandos para memorizar. Ahora... se siente más como una línea de tiempo. Un registro de cómo evolucionó una idea.

Cada commit representa una pequeña decisión. Cada rama representa un experimento. Y cada fusión cuenta parte de la historia del software. Creo que es una hermosa manera de ver el control de versiones.

Cosas Que Quiero Recordar 💖

  • ✦Git y GitHub son cosas diferentes.
  • ✦Los commits deben explicar el por qué, no solo el qué.
  • ✦Las ramas hacen que la experimentación sea segura.
  • ✦Los conflictos de fusión son conversaciones, no desastres.
  • ✦El control de versiones es una de las herramientas más importantes que un desarrollador puede aprender.
